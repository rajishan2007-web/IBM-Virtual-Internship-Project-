Must FixF1 · Plaintext demo passwords exposed in login.html

login.html:43–47 renders faculty123 and student123 in plain text inside a "Demo Login Credentials" box that is visible to every visitor — logged in or not. This ships the same credentials that were removed from seed.py stdout back into the production UI.

Should Fix — 3 issues

Should FixF2 · HTML/server mismatch on attendance total_classes minimum

The attendance form in attendance.html:44 sets min="1" on the Total Classes input, preventing a value of 0 in the browser. However, the server-side validation in faculty.py:315 accepts total_cls < 0 as the failure condition — meaning total_cls = 0 passes server validation.

If the browser constraint is bypassed (e.g. via curl or DevTools), a faculty member can save 0 total classes, which writes percentage = 0.0 to the database and makes the student appear to have 0% attendance rather than "no data". This is misleading and can incorrectly trigger the "Needs Attention" classification.

Recommended fixChange the server check in faculty.py from total_cls < 0 to total_cls <= 0, making it consistent with the min="1" HTML constraint.
Should FixF3 · Faculty dashboard "Good Performance" card is arithmetically wrong

faculty_dashboard.html:117 shows a "Good Performance" count as {{ total_students - needs_attention_count }}. This subtracts only the "Needs Attention" students from the total, so it incorrectly includes "Average Performance" students in the green "Good" card. For example, with 2 Good, 2 Average, and 1 Needs Attention out of 5 students, the card would display 4 instead of 2.

The analytics route already passes the correct good_count to analytics.html, but the faculty dashboard computes it incorrectly in the template itself.

Recommended fixPass a good_count variable from faculty.py/dashboard() to the template (it is already computed in the loop: count students where status == 'Good Performance'), then replace the template expression with {{ good_count }}.

Minor — 3 issues

MinorF5 · SESSION_COOKIE_SECURE blocks login over plain HTTP in development

config.py:17 sets SESSION_COOKIE_SECURE = True. This is the correct production setting, but it means the browser will not send the session cookie over plain HTTP. As a result, a developer who runs python run.py locally (plain HTTP) and logs in will be redirected to the login page on every protected route, appearing as though authentication is broken.

The README.md mentions this, but the code has no development configuration class to override it — the only escape is editing config.py directly, which risks accidentally committing the change.

Recommended fixAdd a DevConfig(Config) class that overrides SESSION_COOKIE_SECURE = False, and load it when FLASK_ENV=development or FLASK_DEBUG=true is set. No change to the production Config is needed.
MinorF6 · Chart.js loaded on every page, even those with no charts

base.html:113 loads Chart.js from CDN unconditionally on every page — including the login page, student management, subject management, marks, and attendance pages, none of which render a <canvas> element. This is an unnecessary network request (~200 KB minified) on five of the nine templates.

In addition, dashboard.js is also loaded on every page via base.html:115. The two functions it defines (renderStudentCharts, renderAnalyticsCharts) are only called from the student dashboard and analytics templates.

Recommended fixMove the Chart.js and dashboard.js script tags from base.html into the {% block scripts %} of the two templates that actually need them (student_dashboard.html and analytics.html).
MinorF7 · No empty-state message on faculty dashboard when no students exist

The faculty dashboard renders normally when there are no students — it shows all-zero stat cards and the "Quick Actions" and "Performance Classification Rules" sections, which is fine. However, the "Good Performance" card (F3 above) would show 0 - 0 = 0, and the Needs Attention sections simply do not appear (correctly guarded by {% if attention_students %}).

More practically: if the database is freshly created and the faculty visits their dashboard before adding any students, there is no prompt to add a student — just empty zeros. A brief "No students enrolled yet" hint at the top of the dashboard would improve the first-run experience.

Recommended fixAdd a conditional block at the top of the dashboard content: {% if total_students == 0 %}<div class="alert alert-info">No students enrolled yet. <a href="...">Add your first student</a> to get started.</div>{% endif %}.
